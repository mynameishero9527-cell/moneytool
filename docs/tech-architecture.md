| 项 | 内容 |
| --- | --- |

本文回答需求「怎么实现」：分几层、每层用什么、数据从哪来、口径怎么统一、盘中怎么算、回看怎么保证一致。不重复需求里的业务规则，只引用章节号。

## 1. 需求对架构的硬约束

从需求里抽出来的、直接决定技术选择的条件：

| 约束 | 出处 | 对架构的要求 |
| --- | --- | --- |
| 资金流全产品一个口径，不同来源不相加 | 6 | 不能日频用 A 厂商、盘中用 B 厂商拼接 |
| 第一版就有盘中 5 个分段 + 9:25 竞价 | 7、11.2 | 需要盘中可得的资金流；厂商日频接口做不到 |
| 阶段、名单每日收盘存档，回看用当日存档和当日参数版本 | 9.7、13 | 结果表按交易日快照，参数表有版本；不能回看时重算 |
| 板块成分、指数成分、概念成分用当日生效版本 | 11.1 | 成分表带生效区间，不是覆盖式更新 |
| 同一参数版本、同一日数据，重复计算结果一致 | 13 | 计算纯函数化，不依赖运行时刻 |
| 周期性归因需要 5 年日线，低位企稳需要 250 日 | 7.5、8.9 | 历史数据至少回补 5 年 |
| 规则可解释，每个标签输出命中的条目 | 7.1、8.3 | 规则引擎输出证据结构，不是只输出结论 |
| 事后统计按参数版本分组 | 9.7.1 | 存档时记录参数版本号 |

结论先给：资金流**自己算**。从逐笔成交或 3 秒快照按需求 6 节的分单规则（超大 / 大 / 中 / 小）在自己的库里聚合，日频和盘中分段用同一套代码产出，口径自然一致。厂商的日频资金流只用来做对账校验，不进产品。

## 2. 总体架构

```text
┌──────────────────────────────────────────────────────────────────┐
│  数据接入层  (Ingestion)                                          │
│  行情源适配器 │ 参考数据适配器 │ 公告与外部资产适配器 │ 回补任务     │
└───────────────┬──────────────────────────────────────────────────┘
                │ 原始表（不改写，只追加）
┌───────────────▼──────────────────────────────────────────────────┐
│  计算层  (Compute)                                                │
│  资金流聚合 → 指标派生 → 板块阶段 → 个股角色 → 名单与标签 → 存档    │
│  参数版本 │ 规则引擎（带证据输出） │ 盘中增量 / 收盘全量 两种模式    │
└───────────────┬──────────────────────────────────────────────────┘
                │ 结果快照表（按交易日 + 参数版本）
┌───────────────▼──────────────────────────────────────────────────┐
│  服务层  (API)                                                    │
│  查询 API │ 提醒推送 │ 回看 │ 事后统计聚合 │ 口径与参数只读接口     │
└───────────────┬──────────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────────┐
│  展示层  (Web)                                                    │
│  看板 │ 多板块对比 │ 板块详情 │ 个股页 │ 行动清单 │ 自选 │ 回看     │
└──────────────────────────────────────────────────────────────────┘
```

四层之间只通过表和接口通信。计算层不直接读厂商接口，展示层不直接算指标。这样回看只需读快照，盘中和收盘走同一套计算代码。

## 3. 数据接入层

### 3.1 数据源选择

| 数据 | 首选源 | 备选 | 说明 |
| --- | --- | --- | --- |
| 逐笔成交 / 3 秒快照（算资金流用） | 券商 QMT（迅投）行情接口，开户后可申请 | 掘金量化、通达信 L2 | 需要 Level-2 逐笔或至少 3 秒快照含分笔成交。这是全系统最关键的一路数据 |
| 日线、复权因子、涨跌停价、停复牌、ST | Tushare Pro（`daily`、`adj_factor`、`stk_limit`、`suspend_d`、`namechange`） | AkShare | 日频参考数据成熟稳定 |
| 申万一级 / 二级成分及变更 | Tushare（`index_classify`、`index_member_all`） | 申万宏源官网 | 需要成分变更历史，用于当日生效版本 |
| 概念成分 | 东方财富 / 同花顺概念（经 AkShare） | Tushare `ths_index` | 概念源不稳定，需每日快照落库，不依赖源方历史 |
| 指数成分（上证 50、沪深 300、中证 500 / 1000 / 2000、创业板指、科创 50） | 中证指数公司、深交所公开成分文件 | Tushare `index_weight` | 月度更新，落库时记录生效日 |
| 自由流通股本、流通市值 | Tushare `daily_basic` | 厂商 | 日频 |
| 股东户数、前十大流通股东 | Tushare `stk_holdernumber`、`top10_floatholders` | 巨潮公告 | 季频，记录披露期 |
| 减持公告、监管处罚 | 巨潮资讯公告抓取 + Tushare `stk_holdertrade` | 交易所监管公开信息 | 处罚数据结构化程度低，第一版用关键词分类，人工复核 |
| 北向公开披露 | 港交所 / 上交所公开页面 | Tushare `hk_hold`（季度） | 只取仍披露的项 |
| 外部资产（原油、铜、金、费半、BDI、汇率） | Tushare 期货与国际指数接口 | 公开行情 API | 日频即可，用隔夜收益 |
| 集合竞价 | QMT 9:25 快照 | Tushare 实时日线 | 与盘中同源 |

厂商的日频资金流（Tushare `moneyflow`）**只做对账**：每日收盘后比对自算结果与厂商结果的相关性，偏差超阈值告警，排查分单规则或数据缺口。不进入任何产品页面。

### 3.2 资金流自算规则

需求 6 节要求超大 / 大 / 中 / 小四档。落地口径：

- 分档按**单笔成交金额**：小单 < 5 万，中单 5–20 万，大单 20–100 万，超大单 ≥ 100 万。这是市场通行口径，也和 Tushare 对账口径一致。
- 方向按主动买卖：逐笔成交里有 BS 标志直接用；只有快照时，用价格相对上一快照买一卖一的位置判定。
- 3 秒快照场景下，一个快照内的成交额合并为一笔，分档会偏向大单。要在口径页写明，并用逐笔数据（若可得）校准阈值。
- 净流入 = 主动买入金额 − 主动卖出金额，按档分别累计。
- 板块净流入 = 成分股净流入求和，一字板成分股按需求 8.1 剔除。
- 分段：按 11.2 的 5 段 + 竞价段，每段落一条累计记录；收盘记录一条日汇总。日汇总与 5 段之和必须相等，作为自检。

### 3.3 接入原则

- 原始数据只追加、不改写。每条带 `source`、`ingested_at`。
- 成分类表用**生效区间**（`effective_from`、`effective_to`），不用覆盖更新。回看某日按区间取。
- 每个适配器有独立的健康检查：最近成功时间、缺口列表。缺口进入 11.3 的「数据缺失」标记，计算层可读。
- 历史回补是独立任务，按数据源分别回补，至少 5 年日线、1 年逐笔 / 快照（用于校准与事后统计）。

## 4. 计算层

### 4.1 分层与依赖

计算按依赖顺序分六步，每一步的输出是下一步的输入，都落表：

```text
① 资金流聚合      个股分段 / 日；板块（一级、二级、概念）分段 / 日；全市场
② 指标派生        6.1 全部派生量：斜率、留存、相对强度、市场份额、超大单占比…
③ 板块阶段        7.1 六阶段 + 优先级 + 防抖 + 迁移路径；7.2 形态；7.5 归因；7.3.1 主线与轮动
④ 个股角色        8.1 强势（核心 / 跟随）、8.2 规避、8.6 身份标签、8.10 排除标签、8.7 评分
⑤ 名单与动作      8.3 买入关注、8.4 卖出关注、8.8 买点卖点、8.9 低位企稳、跟踪闭环
⑥ 存档            按 trade_date + param_version 写快照；盘中写 intraday 表，收盘写 confirmed 表
```

③④ 之间无循环依赖：角色需要阶段（判断能否进买入），阶段不需要角色。⑤ 依赖 ③④。

### 4.2 规则引擎

- 每条规则是纯函数：输入某日某标的的指标向量与参数，输出 `{hit: bool, evidence: [...]}`。证据结构固定：规则名、涉及指标、当日值、阈值、是否命中。
- 阶段判定输出**所有候选阶段的命中情况**，再按 7.1 优先级取最终阶段，被压下的候选进解释区。
- 防抖需要昨日确认阶段，从 confirmed 表读，不从内存读。
- 规则集用声明式配置描述阈值（YAML），逻辑在代码里。阈值配置即参数版本的内容。
- 单元测试用构造的指标向量，覆盖需求 14 节每一条验收标准；集成测试用某几个历史交易日的真实数据做金样本（golden），改规则后先跑金样本比对。

### 4.3 参数版本

- `param_version` 表：版本号、生效交易日、YAML 全文、变更说明。
- 计算任务启动时按交易日取当日生效版本，写进结果快照。
- 改参数只能新增版本，不能改旧版本。
- 事后统计按 `param_version` 分组，直接满足 9.7.1。

### 4.4 盘中与收盘两种模式

同一套代码，两个入口：

| 模式 | 触发 | 输入范围 | 输出 |
| --- | --- | --- | --- |
| 盘中增量 | 每个分段结束 + 1 分钟（10:31、11:31、14:01、14:31、15:01），另有 9:26 竞价 | 当日截至本段的累计资金流 + 历史 confirmed 数据 | 写 `*_intraday` 表，标 segment |
| 收盘全量 | 15:10 起，日线与资金流齐全后 | 当日完整数据 + 历史 | 写 `*_confirmed` 表，触发提醒对账（确认 / 撤销） |

盘中模式下，阶段不切换（需求 7），只输出「盘中倾向」；角色、名单可以变化但标「盘中」。收盘模式是权威结果。

全市场约 5000 只股票、31 个一级、130 个二级、数百个概念。指标计算是向量化的列运算，单机 Polars 或 Pandas 在分钟级完成，不需要分布式。

### 4.5 事后统计

独立任务，每日收盘计算完成后运行：对 N 日前的名单，补齐后续 3 / 5 / 10 / 20 / 30 日走势，写入 `label_outcome` 表。查询时按阶段、组别、买卖点类型、参数版本聚合，样本 < 30 只返回样本数（9.7.1）。

## 5. 存储

### 5.1 选型

| 用途 | 选型 | 理由 |
| --- | --- | --- |
| 逐笔 / 快照原始数据 | Parquet 文件按日分区（对象存储或本地盘） | 只追加、只按日读；压缩比高；不需要数据库 |
| 分段与日频资金流、指标、结果快照 | PostgreSQL + TimescaleDB | 时序表按 trade_date 分块；关系查询（成分、参数版本、用户自选）在同一库 |
| 缓存与提醒队列 | Redis | 看板首页热数据；提醒去重（同标的同事件当日一次）用 key 过期 |
| 分析型大查询（事后统计跨年聚合） | 第一版仍用 PostgreSQL；数据量到十亿行级再评估 ClickHouse | 避免过早引入第二套存储 |

### 5.2 核心表（概要）

| 表 | 主键 | 说明 |
| --- | --- | --- |
| `trade_calendar` | trade_date | 交易日历，含临时休市 |
| `security` | code | 基础信息、交易板块、上市日 |
| `sector` | sector_id | 一级 / 二级 / 概念，含父级 |
| `sector_member` | sector_id, code, effective_from | 生效区间 |
| `index_member` | index_id, code, effective_from | 生效区间 |
| `bar_daily` | code, trade_date | 日线、复权因子、涨跌停价、自由流通市值 |
| `moneyflow_seg` | code, trade_date, segment | 自算分段资金流四档 + 净额 |
| `moneyflow_daily` | code, trade_date | 自算日汇总 |
| `sector_moneyflow_seg` / `_daily` | sector_id, trade_date[, segment] | 板块聚合 |
| `feature_daily` | code / sector_id, trade_date | 6.1 派生量 |
| `sector_stage_confirmed` | sector_id, trade_date | 阶段、候选、迁移标记、形态、归因分、param_version |
| `sector_stage_intraday` | sector_id, trade_date, segment | 盘中倾向 |
| `stock_role_confirmed` | code, sector_id, trade_date | 角色、标签、评分及分项、证据 JSON |
| `action_list_confirmed` | code, sector_id, trade_date, list_type | 买入 / 卖出 / 低位企稳 / 跟踪中，含买卖点类型、证据 JSON |
| `*_intraday` | 同上 + segment | 盘中版 |
| `tracking` | code, entered_date | 跟踪闭环状态 |
| `label_outcome` | list_type, code, entered_date, horizon | 事后统计 |
| `param_version` | version | YAML、生效日 |
| `external_asset_map` | sector_id | 7.5 映射表 |
| `user_watchlist` / `alert_log` | user_id, … | 自选与提醒记录 |

证据用 JSONB 存，查询时不需要拆字段，展示时直接渲染。

## 6. 服务层

- 框架：Python FastAPI。计算层与服务层同语言，共享指标定义和参数解析代码，避免两套口径。
- 接口分组：市场总览、板块（列表 / 详情 / 对比）、个股、行动清单、自选与提醒、回看、事后统计、口径与参数（只读）。
- 所有查询接口接受 `trade_date` 参数，缺省为最近交易日；有值即回看，读该日快照。盘中接口另有 `segment`。
- 响应中每个数字带口径元信息（估算 / 已确认 / 盘中、参数版本），满足需求 13 「口径在数字旁边可见」。
- 提醒：计算任务完成后发事件到 Redis Stream，提醒服务消费，做去重、限频（9.6），推送渠道第一版只做站内 + 邮件 / 企业微信 Webhook 之一。
- 鉴权：第一版单用户或少量用户，简单 Token；自选和提醒按用户隔离。

## 7. 展示层

- 框架：Next.js（React + TypeScript），服务端渲染首屏看板，客户端拉盘中增量。
- 图表：ECharts。多板块对比（9.2.1）、资金曲线、阶段色带、同月历史柱状、外部资产叠加都在 ECharts 内实现，不引入第二套图表库。
- 状态：TanStack Query 管接口缓存与盘中轮询（分段结束后拉一次即可，不需要 WebSocket）。
- 表格：TanStack Table，看板和行动清单的折叠（一级 → 二级）、排序切换（留存 / 评分）、今日新增 / 移出筛选。
- 移动端：响应式，盘中优先保证阶段、一日变化、行动清单三块（需求 10）。
- 所有标签、证据、失效条件用同一个「证据卡片」组件渲染 JSON 证据，规则新增时前端不用改。

## 8. 调度

- 调度器：Prefect（或 Dagster）。任务有依赖图、重试、失败通知、运行历史，比 cron 好排查。第一版单机部署即可。
- 每日流程：

```text
08:30  参考数据同步（日历、停复牌、ST、成分变更、涨跌停价）
09:26  竞价段计算 → 盘前倾向
10:31 / 11:31 / 14:01 / 14:31 / 15:01  分段资金流聚合 → 盘中增量计算 → 盘中提醒
15:10  等待日线与全日资金流齐全 → 收盘全量计算 → 存档 → 提醒确认 / 撤销
16:00  与厂商日频资金流对账 → 偏差告警
19:30  季频 / 公告类数据同步（股东户数、减持、处罚）→ 排除标签重算（次日生效）
20:00  事后统计补齐
```

- 非交易日不产出（11.2、11.3）。临时休市按日历表处理。
- 盘中行情断流：分段任务检测到缺口时，当段标「数据缺失」，不用上一段填。

---

## 9. 部署与运维

- 第一版单机：一台 8 核 32G 云主机跑接入 + 计算 + API + 调度，PostgreSQL 与 Redis 同机或托管。逐笔数据一年约数百 GB Parquet，放对象存储。
- 容器化：Docker Compose 起全部服务；后续需要时迁 Kubernetes。
- 监控：每个任务的完成时间、行数、与前一日的差异比例；资金流对账偏差；API 延迟。Prometheus + Grafana。
- 备份：PostgreSQL 每日全量 + WAL；Parquet 在对象存储自带多副本。
- 行情接口只在境内可用，部署在境内机房。

## 11. 落地顺序（按依赖，不按时间）

每一步完成的判据写在括号里，对应需求验收标准。

1. **数据底座**：日历、证券、成分生效区间、日线回补 5 年；Tushare 适配器与健康检查。（回看任意历史日能取到当日成分）
2. **资金流自算**：QMT 逐笔 / 快照接入，分档聚合，日汇总与厂商对账相关性 ≥ 0.9。（分段之和等于日汇总；对账告警可用）
3. **指标与阶段**：6.1 派生量、7.1 六阶段含优先级与防抖、7.2 形态。（验收 1、2、15、16、17）
4. **角色与标签**：8.1、8.2、8.6、8.7；连板 / 新纳入 / 复牌处理。（验收 3、4、5、10、19、24、25）
5. **名单与闭环**：8.3、8.4、8.8、跟踪中。（验收 8、9、12、18、21）
6. **收盘存档与回看 API**：快照表、参数版本、回看接口。（验收 7、13）
7. **前端 P0 页面**：看板、板块详情、个股页、行动清单。
8. **盘中模式**：分段调度、盘中表、盘中标记、提醒去重。（验收 11、23）
9. **市场层与归因**：7.3.1 主线轮动、7.5 归因、外部资产接入、多板块对比。（验收 26–29、34）
10. **低位企稳与排除标签**：8.9、8.10，季频与公告数据接入。（验收 30–32）
11. **事后统计**：9.7.1。（验收 22）
12. **P1 其余**：自选提醒渠道、参数口径页、自定义阈值隔离。

第 2 步是关键路径。若 QMT 接入受阻，可先用日频厂商资金流完成 3–7 步的开发与验收，但要在口径页标注，并在第 8 步前切到自算，不允许两种口径同时进产品。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 逐笔 / 快照源不稳定或断流 | 盘中分段缺失，阶段不可信 | 分段标「数据缺失」不填补；两路行情源热备；收盘用厂商日频对账发现偏差 |
| 快照合并导致分档偏大单 | 主力净流入系统性偏高 | 用逐笔样本校准阈值；口径页写明；对账偏差纳入告警 |
| 概念成分源不稳定 | 概念阶段跳变、回看不一致 | 每日成分快照落库；连续两日成分变动超 30% 的概念标「成分异常」，不进主线 |
| 处罚、减持公告非结构化 | 历史暴涨暴跌标签漏判或误判 | 第一版关键词分类 + 人工复核队列；个股页展示原文链接 |
| 参数调整后新旧结果混看 | 事后统计失真 | 参数只增不改；所有结果表带版本；统计按版本分组 |
| 规则改动引入回归 | 名单质量下降不易察觉 | 历史交易日金样本比对；验收标准全部转成自动化测试 |
| 单机容量 | 盘中计算超时 | 指标计算向量化；分段任务 5 分钟内完成为目标，超时告警；确有需要再拆计算节点 |
